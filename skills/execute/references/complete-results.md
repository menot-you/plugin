# Complete results

Define the observable result, affected consumer, scope, authority and necessary
proof before changing anything. Scale the record to the task. Use the existing
work panel for a campaign, not a second ledger for each check.

A unit is an independently deliverable result. It may need several observations,
tests or witnesses. Split when outputs, dependencies or ownership genuinely
separate; never split merely because acceptance has two conditions. A commit
preserves work; it does not define completion. Preserve every accepted
requirement, including future stages that are not ready to execute.

For a change, reproduce the intended failure on the affected path before the
implementation, then make the same regression pass. An existing relevant test
can supply that RED; an unavailable runner cannot. Use the smallest executable
check that distinguishes the defect from the correct behavior. Explanations,
lookups and readbacks do not require an invented failing test.

Inspect relevant state, callers and tests together where independent. Fix the
narrowest shared cause. Prefer existing repository mechanisms, standard library
and native capabilities to new layers. Keep code, tests, documentation,
changelog applicability and rollback coherent in the same delivery.

Run the required checks and inspect the actual consumer result. Reuse valid
observations; repeat a check only when a relevant input changed or a remaining
question needs a different observation. Do not add tests that merely restate the
implementation. The checks and limits the repository declares, and accepted
proof obligations, remain binding: they cannot be deferred out of the candidate or
lowered to make it pass. A permitted exception follows the repository's own dated
exception record and preserves the failed measurement.

A gate failure outside the authorized change is a finding, not a new assignment.
Separate inherited debt from introduced regression. A no-regression verdict
does not satisfy a new requirement by itself.
